# 加锁超时残留锁修复

## 问题与边界

1. Redis 可能已经写入锁，但调用方因超时或连接错误未收到成功响应。当前代码只释放进程内等待状态，Redis 锁可能残留至 20–30 秒有效期结束。
2. Redis 客户端还可能自动重试：第一次写入成功但响应丢失，第二次普通 SET NX 返回失败，调用方仍不知道自己已持锁。
3. 本次修复上述可复现的失败路径，不将其表述为已确认的线上事故根因。

## 设计决策

1. 保留 redislock v0.7.2、现有公开接口、token 格式、锁有效期、续期和释放流程。
2. 在传入 redislock 的 Redis 客户端外增加内部适配层。加锁使用原子 Lua：只有 key 不存在才创建；若完整锁值与本次 token 和 metadata 完全相同，则视为同一次请求重试成功，并重新设置原定有效期，避免向调用方返回即将过期的锁；其他持有者仍返回失败。
3. Redis 命令返回错误时，用独立于调用方的 1 秒超时执行原子比较删除，只删除本次完整锁值。清理成功与失败均记录 key 和错误，保留原始加锁错误，不输出 token。
4. 清理使用 EVAL 直接执行，避免首次清理还要加载脚本。Redis 故障或跨连接命令乱序仍可能导致清理失败或先于延迟的写入执行；这时只能由原有效期兜底，不能保证所有网络故障下即时清理。
5. 单次加锁失败最多增加 1 秒同步清理时间；正常加锁使用缓存 Lua，保持一次 Redis 往返，不为正常锁竞争增加清理请求。

## 验证

1. 仅运行本次新增测试，显式列出生产文件与新测试文件，不加载或运行原有测试。
2. 使用测试专用内存 Redis（miniredis），不连接本地或生产 Redis。
3. 验证写入成功后响应超时可以清理并重新获取；替换为其他持有者后不会误删；普通持有者竞争不会误删；成功获取、续期、释放仍可用。
4. 注入真实客户端读响应失败，验证自动重试能够识别自己已写入的锁；清理失败能够记录日志并保留原始错误。
